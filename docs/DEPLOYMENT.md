# Подготовка EKT к размещению в Railway

Публикуется отдельное веб-приложение из изолированного Docker context `deploy/railway`. Сборщик не создаёт проект Railway, не выполняет деплой и не читает значения ключей. Создание нового проекта и публикацию выполняет основная сессия после проверки комплекта.

## Сборка в Windows

Из корня проекта:

```powershell
.\.venv\Scripts\python.exe scripts\build_deploy.py
.\.venv\Scripts\python.exe scripts\build_deploy.py --check
```

Скрипт использует только стандартную библиотеку Python. При недоступном проектном интерпретаторе его можно выполнить через bundled Python Codex. Повторный запуск заменяет только проверенный фиксированный каталог `deploy/railway`; остальные файлы проекта не затрагиваются.

В `deploy/railway-manifest.json` записываются относительные пути, размеры и SHA-256 файлов. `--check` дополнительно сверяет комплект с текущими исходниками: после любого исправления приложения сборку нужно повторить. Весь `deploy/` исключён из Git.

## Состав комплекта

- Файлы непосредственно в `app/` с расширениями `.py`, `.html`, `.css`, `.js`.
- `scripts/run_site.py`, `requirements.txt`, `Dockerfile`.
- Только каталожный seed `data/raw_details.jsonl`.
- Статические ресурсы из `дизайн/assets/`.

`.env`, локальные SQLite и WAL/SHM, история диалогов, корзины, CMS-состояние, журнал метрик, PID, логи, виртуальное окружение и Git не копируются. Сборщик проверяет точное совпадение с allowlist, синтаксис Python, импорты, локальные ресурсы интерфейса, уникальность идентификаторов seed и обязательные поля товаров. Значения, похожие на API-ключи в исходниках приложения, останавливают сборку без вывода самих значений.

## Linux-контейнер

Dockerfile использует `python:3.13-slim`, устанавливает зависимости из `requirements.txt` и `fonts-dejavu-core`. PDF выбирает Linux-шрифт `/usr/share/fonts/truetype/dejavu/DejaVuSans.ttf`; Windows-путь Arial в коде является необязательным вариантом поиска. Все пути приложения вычисляются относительно корня через `pathlib`.

`run_site.py` принимает адрес из `HOST` и порт из `PORT`, запускает один процесс сайта и отключает Telegram polling. Существующий Telegram-процесс не следует включать повторно в веб-сервисе. Для русского текста используются UTF-8-файлы и встроенный в PDF шрифт.

При доступном Docker Engine локальная проверка контейнера:

```powershell
docker build -t ekt-assistant-review .\deploy\railway
docker run --rm -p 8001:8001 --env PORT=8001 --env HOST=0.0.0.0 ekt-assistant-review
Invoke-WebRequest http://127.0.0.1:8001/health
```

Этот запуск без переменных доступа проверяет старт, каталог и HTTP. Вызовы OpenAI, обновление EKT и удалённый доступ CMS требуют переменных сервиса. Отсутствующие ключи не подставляются из файлов сборки.

## Настройки нового сервиса Railway

Docker context — `deploy/railway`, Dockerfile — в корне этого context. Сервис должен получать `HOST=0.0.0.0`, Railway `PORT`, публичный `PUBLIC_BASE_URL` после назначения домена, `OPENAI_API_KEY`, `OPENAI_MODEL`, `OPENAI_RESEARCH_MODEL`, `EKT_API_BASE`, `EKT_API_USER` и `EKT_API_PASSWORD`. Значения задаются переменными Railway, а не файлами сборки. `CMS_ADMIN_TOKEN` обязателен для удалённого административного API; его значение не включается в отчёты или команды документации.

Постоянный volume монтируется в `/app/data`. Docker кладёт исходный каталог отдельно в `/app/seed/raw_details.jsonl`. При первом запуске `run_site.py` копирует его в пустой volume только если ещё нет `catalog.sqlite` и `raw_details.jsonl`. Дальше сохраняются локальная БД каталога, история ассистента, корзины, задачи CMS и метрики. Новый комплект не содержит пользовательские данные с рабочей машины.

Синхронизация запускается каждые 300 секунд. Полный перечень обновляется отдельно от остатков: детали обновляются ограниченными партиями и непосредственно при подтверждении корзины. Экран CMS показывает время последней полной загрузки списка, очередь карточек и покрытие свежими остатками. Общая SQLite lease исключает одновременные полные обходы одной БД несколькими процессами.

## Проверка опубликованного сервиса

1. `GET /health` возвращает `200`, количество товаров больше нуля.
2. `/` и `/admin` открываются; `/static/site.css`, `/static/site.js`, `/assets/`-ресурсы доступны.
3. Защищённый `/api/admin/summary` без токена возвращает `401`, с корректным токеном — `200`.
4. Запрос известного артикула возвращает каталожные сведения; без подтверждения корзина не меняется.
5. После явного подтверждения корзина содержит допустимое количество и открывается по выданной ссылке.
6. `/api/admin/catalog-sync` показывает живое состояние; экспорт XLSX/PDF работает с административным токеном.
7. После перезапуска сервиса сохранённые задачи CMS и локальное состояние остаются в volume.

Проверки с изменением состояния выполняются только на новом тестовом сервисе. Подготовка комплекта сама по себе не означает, что деплой или внешний smoke уже выполнены.

## Фактически выполненная проверка

На этой машине Docker CLI установлен, но Linux Engine не запущен: `docker version` не нашёл pipe `dockerDesktopLinuxEngine`. Поэтому локальный Linux image пока не собран; выполнена статическая проверка Dockerfile, зависимостей, путей, шрифтов и состава комплекта. Реальную сборку и HTTP smoke нужно подтвердить результатом Railway build/deploy либо запуском Docker Engine.

Сборка 23.09.2026 содержит 33 файла, 49 299 711 байт и 15 035 каталожных позиций. `build_deploy.py --check` подтвердил совпадение с исходниками; 16 Python-файлов скомпилированы без записи `__pycache__`, локальные ресурсы и объявленные зависимости присутствуют. Запрещённых файлов в комплекте: 0. По категориям исключены 2 файла окружения, 9 файлов баз/состояния, 7 логов/PID и журнал метрик ассистента. Актуальные числа после следующей сборки находятся в manifest.

Контрольный read-only запрос первой страницы EKT (`page=1`, `per_page=1000`) вернул HTTP 200 и 1000 позиций за 11,964 секунды. Поэтому таймаут фоновой загрузки списка увеличен до 20 секунд при общем ограничении прохода 240 секунд; фоновые детали сохраняют таймаут 5 секунд. Быстрый поиск по утверждению клиента остаётся ограничен 1,9 секунды, проверка остатков при подтверждении — 1,6 секунды. После изменения прошли все 17 тестов синхронизации без внешних сетевых запросов.
